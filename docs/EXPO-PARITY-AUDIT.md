# مراجعة تطابق Expo مع الموقع

تاريخ: 2026-09-11. مراجعة الكود المحلي، وليست شهادة تطابق مع النسخة المنشورة أو اختبار شراء أو حساب مشترك فعلي. لم تُعدّل وظائف ضمن هذه المراجعة.

## النتيجة

Expo واجهة جزئية لنفس الخدمة، وليس بديلًا مكافئًا وظيفيًا حتى الآن. مشاركة Convex وقواعد الاشتراك أساس جيد، لكنها لا تعني أن مسارات المستخدم مكتملة. يجب تثبيت الوظائف قبل المزيد من إعادة التصميم.

| المسار | الموقع المحلي | Expo الحالي | الأولوية |
|---|---|---|---|
| الباقات | PublicPlansNew ومسارات PayLater ونتيجته | مدد وخيارات من الخدمة نفسها؛ الضغط يفتح واتساب | عالية: اختيار واضح ثم مسارات الاشتراك نفسها |
| المنيو | تصفح واختيار للمشترك ومراجعة طلب | بحث وتصنيفات وتفاصيل للتصفح فقط | حرجة: نقل رحلة الاختيار كاملة بعد اختبارات القواعد |
| أسابيع الطبخ | فترات الاشتراك، أيام التوصيل، أسابيع الدوران وحدود الاختيار | تصدير shared/rules موجود، لا توجد شاشة اختيار مكافئة | حرجة |
| الحساب | دخول، تسجيل، استعادة، ملف وإدارة اشتراك | دخول وملف للقراءة؛ الاستعادة والاختيار يفتحان الموقع | عالية |
| استمرار الجلسة | جلسة الموقع | جلسة في ذاكرة التطبيق فقط؛ لا تنتقل تلقائيًا للمتصفح | عالية: تخزين آمن ومعالجة انتهاء الجلسة |
| خدمات المشترك | توقف/تخطي أيام، إشعارات، ولاء، حذف حساب | غير منفذة أصليًا | عالية مع مراجعة صلاحيات كل عملية |
| اللغة | عربي وإنجليزي | النصوص الأساسية عربية ثابتة | متوسطة: مشاركة المصطلحات وإضافة اللغة |
| الصفحات المساندة | الخصوصية والشروط والتواصل والحاسبة والتتبع | لا توجد شاشات أصلية مكافئة في شجرة المسارات | متوسطة؛ الروابط القانونية مطلوبة قبل الإصدار |
| الطاقم والمطبخ | مسارات عمل كاملة في الويب | مدخل WebView/iframe إلى الموقع | الاحتفاظ به مؤقتًا وعدم الادعاء أنه مطبخ أصلي |
| الصور | مسارات متعددة، وبعضها مباشر أو خاص بـPOS | سجل محلي لـ112 وجبة | استكمال توحيد المستهلكين؛ 28 مطابقة غير محسومة |

## فروق يجب علاجها قبل التسليم

- شاشة خطط Expo تحتوي رقم واتساب احتياطيًا شكليًا؛ لا يجوز استخدامه إذا تعذرت الإعدادات. يلزم حالة عدم توفر واضحة.
- خطط Expo تعرض «جارٍ التحميل» أيضًا عند وصول قائمة فارغة؛ يلزم فصل التحميل والفراغ والخطأ.
- الهاتف في حساب Expo ثابت بينما الرئيسية والخطط تقرآن إعدادات المطعم؛ يلزم مصدر موحد لبيانات التواصل.
- تعريف API في Expo يستخدم any؛ نجاح فحص الأنواع لا يثبت مطابقة عقود الخادم.
- عنوان Convex له قيمة افتراضية في Expo؛ يجب التحقق من تطابق بيئة الموقع والتطبيق قبل اختبارات التكامل، دون نشر أو تغيير البيئة تلقائيًا.
- توحيد الصور المنجز محليًا لا يغطي تلقائيًا كل استعلام مباشر أو صور الطلبات القديمة أو POS. لا تُعدّل سجلات الطلبات التاريخية لمجرد تغيير صورتها المعروضة.

## ترتيب التنفيذ المقترح

1. تثبيت إعدادات الخدمة والتواصل، المسميات، اللغة والهوية؛ عدم بناء تصميم آخر مستقل.
2. الباقات: اختيار عدد الوجبات والسناك بشكل صريح، عرض السعر المطابق، ثم الاشتراك/الدفع مع المحافظة على الخيار المحدد. اختبار الدفع في البيئة التجريبية فقط.
3. الجلسة: تخزين آمن، تسجيل واستعادة، انتهاء جلسة وخروج؛ اختبار حساب تجريبي بدون كشف بياناته.
4. اختيار المشترك: استخدام shared/rules نفسها، نقل أسابيع الطبخ والأيام والحساسية والتعديلات ومراجعة الطلب. التحقق على الخادم أيضًا، وليس في الواجهة فقط.
5. إدارة الاشتراك والإشعارات والولاء ثم الصفحات المساندة. يبقى الطاقم على واجهته الحالية إلى مراجعة منفصلة.
6. مراجعة شكل الموقع وExpo جنبًا إلى جنب بعد اكتمال الرحلات الأساسية.

## بوابة التحقق لكل خطوة

اختبارات حالات الصفر/السناك/الوجبات، بداية ونهاية الاشتراك، الجمعة ودورة الأسابيع، الحساسية، السعر ومعامل التغذية؛ ثم تكامل الحفظ والاسترجاع بحساب تجريبي. مراجعة RTL/LTR والشاشات الضيقة، جهاز iOS وAndroid، والشبكة المنقطعة. اختبارات القواعد الـ13 الحالية خط أساس وليست إثباتًا لاكتمال كل هذه الحالات. لا شراء حقيقي ولا نشر ولا تعديل بيانات إنتاج ضمن المراجعة.
